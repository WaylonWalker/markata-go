# Build Lab and Serial DAG Specification

This document defines the first correctness-oriented build graph boundary for
Markata-Go.  It supplements [LIFECYCLE.md](./LIFECYCLE.md).  The existing nine
lifecycle stages remain compatible metadata and are not replaced by this
specification in the first implementation.

## Build Lab contract

The Build Lab runs real Markata-Go binaries in separate workspaces.  It must
not use process-global `os.Chdir` for subprocess isolation.  Each run receives
an explicit working directory, environment, timeout, captured stdout/stderr,
and process group.  On platforms without a process-group implementation, the
runner rejects the command.  A timeout terminates the complete process group.
The lab pins `HOME`, `XDG_CACHE_HOME`, and temporary directories, and appends a
private merge config after fixture-provided merges.  That config redirects the
built-in build, asset, blogroll, embed, image, mention, Pagefind, Tailwind, and
webmention caches into the workspace.  Cache-related `MARKATA_GO_*` environment
overrides and `MARKATA_GO_SITE_DIR` are ignored, and the child receives an
explicit `--site-dir` for its copied workspace.  Automatic `.env` loading is
disabled for the child build.  Arbitrary custom plugins and untrusted binaries
are not an OS-level sandbox and remain outside this cache redirection contract.
The current process-group implementation supports Linux.

Known generated state such as `output`, `.markata`, `.markata.cache`,
`.markata-cache`, and `cache` is not copied into a clean comparison workspace.
The configured relative output directory is also excluded.  The incremental
candidate workspace retains its own state because that state is the subject of
the incremental comparison.  Derived clean workspaces are removed after their
manifests are captured so large sites do not require several complete output
trees at once.

For a scenario with source site `S` and mutation `M`, the lab supports:

```text
candidate incremental(S -> M(S))
candidate clean(M(S))
baseline clean(M(S))
```

The required correctness laws are:

```text
baseline clean(M(S)) == candidate clean(M(S))
```

If the candidate intentionally changes deterministic output, run the candidate
binary as both baseline and candidate to isolate legacy-versus-DAG behavior.
That control proves graph compatibility under the candidate behavior; it does
not replace a historical-baseline comparison and review of the intentional
output changes.

Comparisons use canonical output manifests.  A manifest includes all
publishable output files and symlinks.  Known transient files generated by
Markata-Go minification and fontpack plugins are excluded:
`.markata-css_minify-cache`, `.markata-js_minify-cache`,
`.markata-fontpack-cache`, and `.markata-fonts.json`.  Each record has a
normalized relative path, streamed SHA-256 digest, byte size, mode, file type,
and output class.  The default class is `deterministic`.  Output classes are:

* `deterministic`: path, type, size, and bytes must match.
* `semantic`: path and type must match; bytes match unless a registered
  semantic comparator defines the contract.
* `secure-nondeterministic`: path and type must match; random bytes are allowed.
* `volatile`: path and type must match; changing values are allowed.

Missing or extra output paths always fail.  A manifest digest is computed from
canonical JSON with sorted records.  Results contain schema version, binary
digests, fixture digest, scenario ID/version/seed, environment/tool metadata,
manifest digests, correctness verdicts, and work/performance observations.

## Scenario language

Scenarios are declarative and versioned.  Supported operations are:

```text
build
write-file
replace-exact
delete-file
rename-file
copy-file
set-config
touch-file
clear-cache
clear-output
```

`replace-exact` requires its old value to exist exactly once.  Violations are
scenario errors.  Shell commands are not part of the normal scenario language.
Every semantic mutation in a stateful generated scenario is followed by an
incremental-vs-clean comparison.  The seed and generated operation sequence
are persisted in the structured result when a run fails.  `clear-output` removes
the effective candidate output directory, including when the candidate uses a
non-default relative output path.

The first build in a scenario primes candidate state.  It is not an
incremental comparison.  A checkpoint records `incremental_applicable=false`
for this build.  Every later build must start from the previous candidate state
without a clean flag.

When determinism checking is enabled, the checkpoint also records the second
candidate clean run.  A failed run or missing manifest makes
`deterministic_equal=false`; the lab must not report a passing verdict when
that check cannot complete.

## Task and artifact contract

The graph API contains:

```go
type TaskID string
type ArtifactID struct { Kind, Key string }
type TaskSpec struct {
    ID       TaskID
    Group    string
    Requires []ArtifactID
    Provides []ArtifactID
    Scope    Scope
}
type TaskResult struct {
    Artifacts   []Artifact
    DynamicDeps []ArtifactID
}
```

Tasks are the computation boundary.  Artifacts are the dependency and cache
boundary.  Services such as the build clock, renderer, template engine,
fetcher, and tool runner are runtime capabilities and are not hidden in
untyped manager-cache keys.

The graph compiler rejects duplicate task IDs, missing providers, dependency
cycles, and ambiguous single-writer artifacts.  External inputs must be
declared.  Compilation and serialization are deterministic.  Dynamic
dependencies are stored with task state and are restored with cached results.

The first scheduler uses `MaxParallel=1`.  It may randomize the choice between
equally-ready tasks by seed.  All legal serial topological orders must produce
the same deterministic artifacts before true concurrency is considered.

## Plugin migration

Plugins remain the configuration and extension boundary.  A plugin can own one
or more tasks.  Existing lifecycle hooks are adapted as exclusive,
non-parallel-safe tasks, preserving stage priority and registration order.
During this compatibility phase, the native spine's manager and plugin tasks
consume graph dependencies for scheduling, invoke the legacy hook against the
configured manager, and snapshot the resulting projection into their declared
artifacts.  They are intentionally exclusive and are not `ParallelSafe`.
Pure native tasks must operate on explicit inputs and outputs and must not rely
on concurrent mutation of shared `*models.Post` or `Manager` state.  The
compatibility adapters must remain serial until that boundary is replaced.

The first native slice is:

```text
SourceManifest -> ParsedPost -> AutoTitle -> InlineTitles -> PostIdentity
    -> PostIndex -> Wikilinks -> MarkdownRender -> ArticleHTML
```

The initial implementation can commit the slice's final projections to the
legacy manager before later lifecycle hooks run.  The projection is a migration
boundary, not the long-term artifact representation.

The graph MUST preserve lifecycle stage boundaries that affect shared runtime
projections.  Before the first render task, it clears the template post/config
projection caches so render hooks observe metadata produced by all transform
tasks.  This is equivalent to the cache reset performed when the legacy
manager enters the Render stage.

## Reproducibility

For deterministic tasks, equal declared inputs, task version, declared
environment, and tool identity must produce equal output bytes.  The Build Lab
pins UTC and the C locale where supported, records Go/runtime/platform details,
and records configured external tool versions.  Encryption remains explicitly
secure-nondeterministic and must not be made deterministic merely to satisfy
byte comparison.

The Build Lab may set `SOURCE_DATE_EPOCH` to a fixed value for reproducible
build-time timestamps.  Date plausibility checks that decide whether published
content belongs in a current-time view, such as feed-listing sparklines, must
use the wall clock rather than that reproducibility clock.  A fixed epoch must
not hide ordinary dated content from correctness fixtures.

The repository MUST include a checked-in CLI equivalence fixture.  Its test
MUST run the real Markata-Go binary in legacy and `--dag` modes, perform an
initial build, mutate a linked or embedded source, and compare the subsequent
incremental and clean outputs.  The test MUST also exercise candidate clean
determinism and use dates that are valid for the wall-clock plausibility rules.
The fixture SHOULD also cover unresolved links or embeds becoming resolvable,
as well as a source rename, because target availability changes the output of
otherwise unchanged sources.  Global reductions such as link indexes MUST
consume the complete current post set, or restore equivalent cached inputs,
before they assign aggregate results.
